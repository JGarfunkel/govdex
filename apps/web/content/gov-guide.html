Guide for Governments

Most of the information residents need is already collected and already posted. The gap is between posted and findable, and six things commonly stand in the way. They are listed here from the most basic to the most ambitious. The first five make data that already exists easier to reach. The last publishes something most bodies track but never show.

1. Don’t block automated access

Bot rejection is the severe one. When a page blocks automated requests — through a CAPTCHA, an aggressive bot filter, or content that only appears after running JavaScript — it makes public data unusable at scale. A person can still read it one page at a time. A directory that has to keep it current for every town in the state cannot do that by hand. The data is public but effectively out of reach.

This is worth separating from data that was never collected. In one respect blocking is worse: someone did the work of publishing, then removed the value of it by making the result un-reusable.

What to do:

  • Allow well-behaved automated requests to public pages. Set a rate limit if traffic is a concern, and stop short of blocking automated reads entirely.
  • Don’t require JavaScript to display content that could be plain HTML.
  • Don’t put a CAPTCHA in front of a public roster, calendar, or budget.
  • If you have to limit traffic, publish a bulk export so nobody needs to crawl the site page by page.

2. Publish in a machine-readable format

A page can be reachable and still be useless to a machine when the data inside is in the wrong format. A budget posted as a scanned PDF is a picture of a table. A roster inside a Word file, or a list saved as an image to stop scrapers, has the same problem: a person can read it, and no tool can pull the data out without guesswork.

Structured text is the goal. Where the thing has to be a document, make it text a machine can select and extract instead of an image of text.

What to do:

  • Publish tabular data as CSV, JSON, or an HTML table. Keep it out of PDFs and images.
  • If a PDF is required, generate it from text so its contents can be selected and extracted, and avoid scanning paper.
  • Don’t post rosters, budgets, or contact lists as images.
  • Keep a structured version alongside any formatted one. A budget can have both a readable PDF and a CSV of the same numbers.

3. Offer an API or a structured export

The practical answer here is usually the vendor. Records and website vendors increasingly expose the data they hold through an API — Granicus’s Legistar Web API is one example. If your agendas, legislation, or budget already sit in a vendor system, the API may exist already and only need turning on.

What to do:

  • Ask your current vendor whether it offers a public API or a scheduled export, and turn it on.
  • Make an open API or export a requirement the next time you procure or renew a system.
  • Where no vendor covers a dataset, publish a scheduled CSV or JSON file at a stable URL yourself.

4. Give each resource a permanent page

Every standing resource — the budget, the meeting calendar, the committee list — should live at its own stable URL. A resident should be able to bookmark that address and share it, and a tool should be able to check the same address next month and find the current version. The address stays the same as the content behind it changes.

Common failures:

  • The committee list is reachable only by clicking through a menu and has no address of its own.
  • The committee list is broken up into arbitrary alphabetical buckets (A-C, D-P, R-Z).
  • The budget gets a new link each year; there is no permanent page /budget that links to the current budget (and past and future ones).
  • The document lives inside a portal that hands out a temporary link.

What to do:

  • One durable URL per resource. When the content changes, update the page and keep the address.
  • Make the address human-readable where you can: /budget, /calendar, /committees.
  • Show when the page was last updated, so a resident can judge whether it is current and a tool can tell when it changed.
  • If a resource lives only inside a third-party portal, publish a permanent page on your own site that links into it.

5. Make it findable by search

A permanent page only helps if a resident can find it. Most residents look for a committee or a document by typing its name into a search engine. A government site’s own menus are the last place they look. A page that search engines can’t index might as well not be public, because the people searching for it never arrive.

Three things commonly hide a public page from search: a noindex tag, a robots.txt rule that blocks crawlers, and content that lives only behind a site’s own search box with no page of its own to link to.

What to do:

  • Let search engines index public pages. Remove noindex and clear the robots.txt rules that block content meant to be found.
  • Give every resource a browsable, linkable page, not only a result inside a search box.
  • Write plain page titles and headings that match what a resident would type: the committee’s name, the year of the budget, the word “agenda.”
  • Keep a simple index or sitemap listing the permanent pages, so residents and search engines can both discover them.

6. Publish the state of the work, not just the meetings

Open-meetings law requires agendas and minutes, and publishing them counts as openness. What it produces is a snapshot: a fixed record of what a body discussed on a given day. Snapshots matter. Minutes, agendas, and adopted budgets are the legal record, they have to be preserved exactly as they were, and a resident checking what was decided last March needs them intact.

Someone who wants the status of a sidewalk repair, a grant application, or a zoning review should not have to read six months of minutes to piece it together. The question they actually ask is simpler: what is this body working on, and where does each thing stand?

Residents want the stateful record far more often than the snapshot. They reach for the archive occasionally, to confirm what was decided. They rely on the current status all the time. Bodies publish the archive because the law requires it and leave the status unpublished, so the thing residents use most is the thing they can’t get.

Software teams answered this years ago. Every open item has a page with a title, an owner, a status, and a history, and anyone can see what is in progress, what is stuck, and what is finished. A public body’s work fits the same shape: projects, issues, and tasks, each with a current status.

The answer here is usually the same as section 3: a govtech vendor. The status of permits, cases, and legislation often already lives inside a system the body runs, so the work is exposing what that system holds rather than building something new. Where no such system is in place, even a public list with one row per open item and a status column beats leaving residents to reconstruct it from minutes.
